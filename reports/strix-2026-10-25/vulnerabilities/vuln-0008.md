# Future-dated KEV response freezes the saved KEV copy until the operator intervenes

**ID:** vuln-0008
**Severity:** LOW
**Found:** 2026-10-25 15:44:25 UTC
**Target:** cra-scan CLI, KEV download (www.cisa.gov known_exploited_vulnerabilities.json), src/news_watcher.py
**Endpoint:** cra run (fetch_kev -> validate_kev)
**Method:** GET
**CWE:** CWE-345
**CVSS:** 3.7
**Confidence:** High
**Fix Effort:** Trivial

## Description

`validate_kev` accepts any well-formed `dateReleased`, including dates far in the future. One intercepted KEV response with a future date replaces the saved good copy. Every later genuine KEV download is then rejected as "older than the saved copy (possible replay)", so the tool keeps using the frozen copy and no longer picks up new KEV entries until the operator deletes the cache file.

## Evidence

Reproduction against the unmodified source:

```text
1. genuine list           : ok - downloaded and checked
2. future-dated list      : ok - downloaded and checked
3. genuine newer list     : stale - download failed (KEV dateReleased is older than the saved copy (possible replay)); using the saved copy
```

End-to-end `cra run` (same product as the other KEV reports) on the unmodified source:

```text
F-2 future-dated feed
  Source KEV: ok - downloaded and checked
  exit=3 run.complete=True
F-3 genuine newer feed
  Source KEV: stale - download failed (KEV dateReleased is older than the saved copy (possible replay)); using the saved copy
  RESULT INCOMPLETE - do not rely on this.
  exit=3 run.complete=False
  CVE-2026-99999 in saved copy: False; saved dateReleased: 2099-01-01T00:00:00Z
```

After the fix, the future-dated response is rejected at step 2 (`KEV dateReleased is in the future`) and the genuine newer list is accepted with the new CVE present.

## Impact

A single on-path response with a future `dateReleased` makes the KEV source `stale` on every later run, so each run is marked RESULT INCOMPLETE and newly added KEV entries are never recognised. Affected components with no KEV match are then routed to urgent human review rather than checked against the current list. The condition persists until someone deletes the saved KEV file, and the status message blames a "possible replay" that did not happen.

## Counterevidence

(1) The attacker needs an on-path position with a trusted certificate for www.cisa.gov, the same precondition as the other KEV finding. (2) The impact is a persistent but visible state: every run prints `Source KEV: stale` and `RESULT INCOMPLETE`, so the operator is alerted, and the matcher escalates unmatched findings to urgent human review instead of marking them not exploited. That limits the consequence to availability and operator workload, which is why the rating is Low. (3) Deleting the saved KEV file clears the freeze, so recovery is possible. I checked whether a future date could be used to suppress a silent verdict: `src/matcher.py` gates non-exploited findings on `kev_ok`, so no silent "not exploited" result was produced in the reproduction.

## Confidence Rationale

Reproduced end to end on the real KEV code path (fetch_kev, validate_kev, saved copy, run record) with the same simulated on-path response as the other KEV report.

## What Would Change This Severity

If the freeze could be made silent (for example, if the matcher trusted the frozen copy without the stale status gate), the rating would rise to Medium; a check that the saved copy is not older than the stale threshold would lower the rating to informational.

## Technical Analysis

`validate_kev` checks that `dateReleased` parses as a timezone-aware time, but has no upper bound:

```python title=src/news_watcher.py startLineNumber=198 endLineNumber=199
    if released is None:
        return "KEV dateReleased is not a valid time"
```

The replay check in the same function then compares every later genuine download against this future value:

```python title=src/news_watcher.py startLineNumber=228 endLineNumber=230
    saved_time = _parse_time(saved_released)
    if saved_time is not None and released < saved_time:
        return "KEV dateReleased is older than the saved copy (possible replay)"
```

A future `saved_released` makes every genuine download "older", so `fetch_kev` falls back to the saved copy (`status: stale`). `fetch_kev` only overwrites the saved copy on a download that passes `validate_kev`, so the frozen copy is never replaced. `load_kev_cache` also re-validates the saved copy with `validate_kev`, which does not reject a future date, so the poisoned copy keeps being loaded.

The matcher gates non-exploited verdicts on the KEV status (`kev_ok` in `src/matcher.py`), so the freeze produces urgent review rather than a silent "not exploited"; the impact is therefore availability and a persistent incomplete state rather than a silent integrity failure.

## Proof of Concept

1. Start with a clean cache folder and run `cra run` against a genuine KEV list (dateReleased 2026-10-20). The KEV status is `ok`.
2. Serve a KEV list with the same entries and `dateReleased` set to `2099-01-01T00:00:00Z`. The response is accepted: KEV status is `ok` and the saved copy now carries the future date.
3. Serve a genuine newer list (dateReleased 2026-10-21) that adds one new KEV CVE. The response is rejected with `possible replay`, the KEV status becomes `stale`, the run is `RESULT INCOMPLETE`, and the new CVE is absent from the saved copy on every later run.

```python
import copy
import json
import sys
import tempfile
from datetime import datetime, timezone
from pathlib import Path

repo = Path(sys.argv[1])
sys.path.insert(0, str(repo))
import src.news_watcher as nw  # noqa: E402

kev = json.loads((repo / "tests" / "fixtures" / "kev.json").read_text())
now = lambda: datetime(2026, 10, 25, 12, 0, 0, tzinfo=timezone.utc)  # noqa: E731
cache = Path(tempfile.mkdtemp())


def fetch(data):
    return lambda url, body=None, max_bytes=0: json.dumps(data).encode()


_, status = nw.fetch_kev(cache, fetch(kev), lambda s: None, now)
print("1. genuine list           :", status["status"], "-", status["detail"])

future = copy.deepcopy(kev)
future["dateReleased"] = "2099-01-01T00:00:00Z"
_, status = nw.fetch_kev(cache, fetch(future), lambda s: None, now)
print("2. future-dated list      :", status["status"], "-", status["detail"])

newer = copy.deepcopy(kev)
newer["vulnerabilities"].append({"cveID": "CVE-2026-99999", "dateAdded": "2026-10-21"})
newer["count"] = len(newer["vulnerabilities"])
newer["dateReleased"] = "2026-10-21T10:00:00.0000Z"
_, status = nw.fetch_kev(cache, fetch(newer), lambda s: None, now)
print("3. genuine newer list     :", status["status"], "-", status["detail"])
```

## Code Analysis

**Location 1:** `src/news_watcher.py` (lines 198-199)
  Reject a KEV dateReleased in the future

  **Suggested Fix:**
```diff
-     if released is None:
-         return "KEV dateReleased is not a valid time"
+     if released is None:
+         return "KEV dateReleased is not a valid time"
+     if released > utc_now() + timedelta(days=1):
+         return "KEV dateReleased is in the future"
```

## Remediation

Reject a KEV `dateReleased` that is later than the current time plus a small clock-skew allowance, in the same validation function that already rejects malformed dates. Keep the rejection in the download path so a rejected response never replaces the saved copy. Also make the saved-copy loader apply the same check so a copy saved before this fix is discarded instead of being loaded.

## Fix Verification

Gate 1, applicability: a two-line insertion after the existing `dateReleased` check; `utc_now` and `timedelta` are already defined and imported in `src/news_watcher.py`. The original lines 198-199 match the `fix_before` text.

Gate 2, security closure: the future-dated list is rejected with `KEV dateReleased is in the future` and the saved copy is not replaced. The genuine newer list is then accepted and includes the new entry (reproducer steps 2 and 3 after the patch).

Gate 3, bypass review: a `dateReleased` up to one day ahead is still accepted, so a freeze of up to one day is possible per intercepted response; the check bounds the freeze rather than removing it. `load_kev_cache` re-runs `validate_kev` on the saved copy, so a copy saved before the patch with a future date is now discarded on load and the next genuine download is accepted, which restores the baseline. Clock skew of more than one day on the operator's machine would reject a genuine list (fail-safe, `stale`).

Gate 4, preserved behaviour: the normal path (`dateReleased` at or before now) is unchanged, and the replay check still rejects older dates.

Gate 5, repository checks: `python3 -m pytest -q` in the copy: 411 passed, 2 skipped, including the new `test_kev_date_released_in_the_future_is_rejected`. The test asserts that the future-dated list is reported as a problem, which the unmodified `validate_kev` does not do (the reproducer shows `ok` for the same input).

## Assumptions

The attacker can deliver one modified KEV response to the operator (on-path position with a trusted certificate, as for the other KEV report). The operator then runs `cra run` normally; no operator action is needed to trigger the freeze.
