# Total download deadline is not enforced during reads, so a slow response can stall a run indefinitely

**ID:** vuln-0009
**Severity:** LOW
**Found:** 2026-10-25 15:44:48 UTC
**Target:** cra-scan CLI, OSV and KEV downloads, src/news_watcher.py (http_fetch)
**Endpoint:** cra run (http_fetch -> api.osv.dev / www.cisa.gov)
**Method:** GET
**CWE:** CWE-400
**CVSS:** 3.7
**Confidence:** High
**Fix Effort:** Trivial

## Description

`http_fetch` applies a 120-second total deadline, but checks it only between `read()` calls. `HTTPResponse.read(64 * 1024)` blocks until 64 KB arrive or the connection closes, so a server that sends a byte every few seconds keeps one read open and defeats the deadline. The per-read socket timeout only catches silence longer than 30 seconds, so a drip below that interval stalls `cra run` for as long as the server keeps dribbling bytes.

## Evidence

Unmodified source, shipped constants, local TLS server:

```text
[drip 8 bytes x 20s, REAL caps (120s total / 30s per read)]  160.0s  FetchError status=None msg=download took too long
```

With `TOTAL_SECONDS` lowered to 10 for a faster check (20 bytes, 2 seconds apart):

```text
[drip 20 bytes x 2s, TOTAL_SECONDS=10]   40.0s  FetchError status=None msg=download took too long
```

Unbounded case (100000 bytes, 25 seconds apart), killed by the 200-second hard timeout with no return.

After the fix (`read1`), same server:

```text
[drip 20 bytes x 2s, TOTAL_SECONDS=10]   10.0s  FetchError status=None msg=download took too long
[drip 8 bytes x 20s, REAL caps (120s total / 30s per read)]  120.0s  FetchError status=None msg=download took too long
```

## Impact

An on-path attacker who can serve OSV or KEV responses can make a single download take an unbounded time, which stops the scheduled `cra run` from finishing. No run record is written for the stalled run, so the last saved record ages until `cra status` reports the run as overdue. The check is interrupted only when the operator kills the process.

## Counterevidence

(1) The attacker must control the OSV or KEV response, which needs the same on-path position with a trusted certificate. (2) The stall is visible: the process prints nothing and the operator can kill it, and the previous run record remains available to `cra status`, so the outcome is a delayed or missing check rather than a false result. (3) The 30-second socket timeout does stop idle connections, so only a drip below that interval is a stall; a plain stalled server is bounded. I did not find a control that bounds a slow drip; the deadline in the code is the intended control and it does not hold.

## Confidence Rationale

Reproduced with real socket I/O on the unmodified `http_fetch` through the shipped code path, with the interception position simulated.

## What Would Change This Severity

Showing that the scheduled run is the only check for a time-critical reporting deadline, with no alerting on a missing run, would not change the rating; a demonstrated run-level hang that blocks all sources for more than the reporting window would raise availability to High.

## Technical Analysis

The deadline and the read loop are in `http_fetch`:

```python title=src/news_watcher.py startLineNumber=100 endLineNumber=111
        with opener.open(request, timeout=TIMEOUT_SECONDS) as response:
            expected = response.headers.get("Content-Length")
            chunks, size = [], 0
            while True:
                if time.monotonic() > deadline:
                    raise FetchError("download took too long")
                chunk = response.read(64 * 1024)
                if not chunk:
                    break
```

`http.client.HTTPResponse.read(amt)` on a close-delimited or Content-Length body keeps reading from the socket until `amt` bytes are available or the stream ends. The loop therefore checks the deadline only after a full 64 KB chunk or end-of-stream. The socket timeout (`TIMEOUT_SECONDS`, 30 s) resets with each received byte, so a server that sends one byte every 25 seconds never triggers it.

Measured with the unmodified code against a local TLS server (`TOTAL_SECONDS` = 120 and `TIMEOUT_SECONDS` = 30 as shipped):
- 8 bytes sent 20 seconds apart: the call returned `download took too long` after 160.0 s, after the server closed the stream, not at the 120 s cap.
- 100000 bytes sent 25 seconds apart: no return within the 200-second hard limit used by the test harness, so the call would continue for about 2.5 million seconds.

The unit test for the deadline (`test_http_fetch_overall_time_limit`) mocks `time.monotonic` and does not exercise the blocking read, so it does not catch this.

## Proof of Concept

1. Serve a TLS endpoint that responds with no Content-Length and sends one byte every 25 seconds, indefinitely.
2. Call `http_fetch` on that URL (or run `cra run` with OSV or KEV pointed at it) with the shipped constants.
3. Observe that the call does not return after 120 seconds and keeps reading until the server closes the stream or the process is killed. With a shorter drip (8 bytes, 20 seconds apart) the deadline error appears only at 160 seconds.

````python

except nw.FetchError as error:

```
````

## Code Analysis

**Location 1:** `src/news_watcher.py` (line 106)
  Read in pieces so the deadline is checked after each network chunk

  **Suggested Fix:**
```diff
-                 chunk = response.read(64 * 1024)
+                 chunk = response.read1(64 * 1024)
```

## Remediation

Read the response in small pieces (for example with `read1`) so the deadline check runs after each network chunk, and keep the per-read socket timeout as the bound on silence. Add a regression test that uses a real drip-feeding stream rather than a mocked clock.

## Fix Verification

Gate 1, applicability: a one-call change in `http_fetch`. `read1` is provided by `http.client.HTTPResponse` (Python 3.5+) and returns available bytes after at most one socket read; the original line 106 matches `fix_before`.

Gate 2, security closure: re-ran the drip scenarios against the patched copy. The 20-byte drip with a 10-second cap now stops at 10.0 s (was 40.0 s). The 8-byte drip with the shipped 120-second cap now stops at 120.0 s (was 160.0 s). The deadline is now checked after every network chunk, so the overrun is bounded by the 30-second socket timeout instead of the length of the response.

Gate 3, bypass review: the other read in this function is the one loop; the retry sleeps in `_fetch_json` are bounded (1, 2, 4 seconds). Connection setup is bounded by the same socket timeout. A response that sends one large chunk instantly is capped by `max_bytes` as before. A drip that sends one byte every 29 seconds still takes up to the total deadline plus one socket timeout, which is the intended bound.

Gate 4, preserved behaviour: the function returns the same bytes for normal answers, keeps the size cap, the Content-Length check and the cut-off error. The existing fake response in the tests gained a `read1` method that delegates to `read`, so the existing unit tests exercise the same logic.

Gate 5, repository checks: `python3 -m pytest -q` in the copy: 411 passed, 2 skipped; the `http_fetch` unit tests (size cap, Content-Length, incomplete read, overall time limit) pass with the fake response. The drip scenarios above were run against the real socket path.

## Assumptions

The attacker can answer the OSV or KEV request on the operator's behalf (on-path position with a trusted certificate). The server keeps the connection open and sends at least one byte within every 30 seconds. The run is started by a scheduler or by an operator who does not watch the process.
