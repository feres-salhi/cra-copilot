# Concurrent run records in the same second overwrite each other

**ID:** vuln-0012
**Severity:** LOW
**Found:** 2026-10-25 15:45:46 UTC
**Target:** cra-scan CLI, run record folder, src/news_watcher.py (save_run)
**Endpoint:** cra run (save_run)
**Method:** N/A
**CWE:** CWE-367
**CVSS:** 2.5
**Confidence:** High
**Fix Effort:** Low

## Description

`save_run` checks whether the run file name is free and then writes it in a separate step. Two runs that finish in the same UTC second can both see the name as free and both write it, so the later write replaces the earlier run record. In the measured case, 16 concurrent saves left one or two files on disk. A complete run can therefore replace an incomplete one in the same second, and `cra status` then shows the replacement.

## Evidence

Unmodified source, three repetitions:

```text
16 concurrent saves in the same second -> run files on disk: 1
16 concurrent saves in the same second -> run files on disk: 1
16 concurrent saves in the same second -> run files on disk: 2
```

After the change, three repetitions:

```text
16 concurrent saves in the same second -> run files on disk: 16
16 concurrent saves in the same second -> run files on disk: 16
16 concurrent saves in the same second -> run files on disk: 16
```

## Impact

Two `cra run` processes that finish in the same second (for example an overlapping scheduled job and a manual run) can lose one run record. If the surviving record is a complete run that replaced an incomplete one, `cra status` reports a complete latest run and hides the failure. The impact is limited to the operator's own run history; no remote party can trigger it.

## Counterevidence

(1) No attacker can trigger the race: the run folder and the scheduler are operator-controlled, and the threat model treats them as trusted. (2) The collision needs two runs that finish in the same UTC second, which is uncommon for a scheduled tool; the reproduction forces it with a barrier. (3) The surviving record is still a valid, atomically written file, so there is no corruption and no exposure of data. The effect is limited to losing one record in a rare overlap, which is why the rating is Low and the attack complexity is high. I did not find a control that prevents the overlap.

## Confidence Rationale

Reproduced on the unmodified `save_run` with real threads and the real write path; the trigger is concurrency only, with no attacker involvement.

## What Would Change This Severity

A demonstrated way for a remote or low-privilege party to cause two runs to finish together, or a status path that treats a replaced record as the latest complete run in a way an attacker can exploit, would raise the rating; without that, the finding stays Low.

## Technical Analysis

The name check and the write are separate steps:

```python title=src/news_watcher.py startLineNumber=575 endLineNumber=581
    stamp = now().strftime("%Y-%m-%dT%H-%M-%SZ")
    path = run_dir / f"{stamp}.json"
    counter = 1
    while path.exists():
        counter += 1
        path = run_dir / f"{stamp}-{counter:04d}.json"  # zero-padded so the order stays right
    _write_json_atomic(path, run)
```

`_write_json_atomic` finishes with `os.replace`, which overwrites an existing file. Between `path.exists()` returning False and the replace, another process can create the same name. The write is still atomic, so no partial file is seen, but the earlier record is gone. Run names have one-second resolution, so the window is the time between the check and the replace in two processes that finish in the same second.

Measured on the unmodified source: 16 threads calling `save_run` behind a barrier with a fixed time left 1, 1 and 2 run files in three repetitions, from 16 saves. With an exclusive create (`O_EXCL`) claiming the name first, the same test kept 16 of 16 files in every trial. The existing test `test_save_run_does_not_overwrite_a_run_from_the_same_second` covers only sequential saves, which is why it did not catch this.

## Proof of Concept

1. Use a run folder that is empty.
2. Start 16 threads that each call `save_run` with the same fixed time, released together with a barrier (two overlapping `cra run` processes that finish in the same second produce the same condition).
3. Count the run files afterwards. On the unmodified source the count is far below 16.

```python
import sys
import tempfile
import threading
from datetime import datetime, timezone
from pathlib import Path

repo = Path(sys.argv[1])
sys.path.insert(0, str(repo))
import src.news_watcher as nw  # noqa: E402

runs = Path(tempfile.mkdtemp())
fixed = datetime(2026, 10, 25, 12, 0, 0, tzinfo=timezone.utc)
barrier = threading.Barrier(16)


def saver(index):
    barrier.wait()
    nw.save_run(runs, {"finished_at": fixed.isoformat(), "writer": index}, lambda: fixed)


threads = [threading.Thread(target=saver, args=(i,)) for i in range(16)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("16 concurrent saves in the same second -> run files on disk:", len(list(runs.glob("*.json"))))
```

## Remediation

Claim the run file name atomically before writing it, so that a second process cannot take the same name, and keep the atomic replace for the content. If the claim fails, move to the next numbered name. Add a regression test that runs concurrent saves in one second rather than only sequential ones.

## Fix Verification

Gate 1, applicability: the change is limited to the body of `save_run` (the docstring, the run folder argument and the return value are unchanged). `os` is already imported in `src/news_watcher.py`. The original lines 575-581 match `fix_before`.

Gate 2, security closure: with the change, the 16 concurrent saves produce 16 separate files in three of three repetitions (see evidence). The name is claimed before the write, so a second process moves to the next counter value instead of replacing the first record.

Gate 3, bypass review: the placeholder file is created empty and is then replaced by the atomic write. A reader that loads the folder in between sees an empty file, which `_read_json` returns as unreadable and `load_runs` skips, so the status is not wrongly complete. If the write fails, the placeholder is removed and the error is raised, so no empty record is left behind. The `FileExistsError` path is the only collision path; other `OSError` values propagate as before.

Gate 4, preserved behaviour: the file names (`<stamp>.json`, then `<stamp>-0002.json`, ...) are unchanged, so the time order used by `load_runs` is unchanged. The existing sequential test that checks the same-second naming still applies.

Gate 5, repository checks: `python3 -m pytest -q` in the copy: 411 passed, 2 skipped, including `test_save_run_does_not_overwrite_a_run_from_the_same_second`. Gap: the concurrent case is verified by the reproducer above, not by a new unit test in the suite.

## Assumptions

Two `cra run` invocations (or a run and a failed-run record) use the same run folder and finish in the same UTC second. No network or remote input is needed, and an attacker is not required; the impact depends on operator scheduling.
