# cra status loads every planted run file into memory without a total size budget

**ID:** vuln-0002
**Severity:** LOW
**Found:** 2026-10-25 15:36:07 UTC
**Target:** cra CLI (local, src/news_watcher.py load_runs / _read_json)
**Endpoint:** cra status --runs &lt;folder&gt;
**Method:** LOCAL
**CWE:** CWE-770
**CVSS:** 3.3
**Confidence:** Medium
**Fix Effort:** Medium

## Description

`cra status` reads up to 1000 `*.json` files from the runs folder, each up to 20 MB, and keeps every parsed record in memory, although only the newest and the newest healthy record are used. A folder holding many large files can exhaust memory and make `status` fail.

## Evidence

Measured: 40 files of about 19 MB each (760 MB on disk) gave a peak RSS of 821 MB and a run time of 2.69 s in `cra status`. The run still exited normally, because the padded files lack the fields needed for a real run record. The per-record cost is therefore about 20 MB of RAM and about 0.07 s of CPU per file. The extrapolation to 1000 files (about 20 GB RAM) has not been tested.

## Impact

Denial of service of the `status` command. A local writer to the runs folder can make `status` consume several gigabytes of memory, slow it down, or crash it with a MemoryError. The operator then cannot check the last run. Data is not disclosed and not modified.

## Counterevidence

1. Write access to the runs folder is required, and the project records that local writers are out of its threat model (PROGRESS.md, accepted). 2. Each file is capped at 20 MB and the count at 1000, so the worst case is bounded, though large. 3. A genuine run record is about 13 KB, so an honest folder never comes close to the limit. 4. The impact is availability of the `status` command only; `run` does not read the runs folder. 5. The attacker is not the SBOM supplier. The check that ran was: does the loader bound the total bytes it reads or keeps? It does not.

## Confidence Rationale

Memory use per file was measured (821 MB for 40 files). The 1000-file worst case is extrapolated and was not run, so the stated ceiling is unconfirmed. The exact point of failure depends on the host.

## What Would Change This Severity

Raise to Medium if an automated job runs `cra status` on a shared or network folder that other principals can write to, so that a remote writer can crash the scheduler's health check. Lower to Informational if the 20 MB per-file cap is reduced to a value that makes the total bounded.

## Technical Analysis

`load_runs` selects the newest `MAX_RUN_FILES` (1000) paths by name, and for each one calls `_read_json`, which reads up to `MAX_CACHE_FILE_BYTES` (20 MB) and parses the JSON. Every parsed record that has a string `finished_at` is appended to `runs` and kept until the function returns. `status_summary` then uses only `runs[-1]` and the newest record that passes `run_is_complete`. Per-file size is capped, but the total is not, so memory grows with the file count times the per-file cap.

1. Create a runs folder with 40 files named like `2026-01-01T00-00-NNZ.json`. Each holds `finished_at` and a padding string of about 19 MB, so each file is under the 20 MB cap.

## Remediation

Bound what `status` loads, not only the size of each file. Keep only the newest run and the newest run that passes the completeness check while reading, instead of retaining every record. Add a total byte budget for the run folder. Make a skipped or oversized file visible: if the budget or the count cap drops a newer file, `status` must print a warning and must not report "Latest run: all sources ok.", so that a dropped run cannot hide behind an older healthy run. The project owner should decide the budget size and the wording of that warning.

## Fix Verification

Informational only. No `fix_after` is provided. A correct fix needs a product decision: the size budget, and whether an over-budget or unreadable newer run must turn the status into a warning. Making the wrong choice would hide the latest run behind an older healthy one, which is the failure this tool exists to prevent. The narrowest code change has not been verified by a test run.

## Assumptions

Attacker has write access to the runs folder and can write up to 1000 files. Attacker-controlled size of each file is limited only by the 20 MB per-file cap. The host has less free memory than the total of the planted files, which is a realistic laptop or task-scheduler machine.
