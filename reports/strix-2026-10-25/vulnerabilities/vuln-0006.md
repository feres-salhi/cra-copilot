# Unchecked components recorded as known not exploited when OSV gives no answer

**ID:** vuln-0006
**Severity:** LOW
**Found:** 2026-10-25 15:43:46 UTC
**Target:** cra-scan (src/matcher.py)
**Endpoint:** src/matcher.py::evaluate
**Method:** N/A
**CWE:** CWE-754
**CVSS:** 3.7
**Confidence:** High
**Fix Effort:** Trivial

## Description

When OSV gives no answer for a component, or the details of a listed advisory cannot be loaded or read, the matcher records the finding as exploited_known = True whenever the KEV list is fresh. The tool never compared that component's CVEs with KEV, yet the finding states that its exploitation status is known and routes it to ordinary human review rather than urgent review.

## Evidence

Observed on the unpatched code, run from the repository root with a fresh KEV list (status ok) that contains CVE-2021-44228:

no OSV answer: osv_gave_no_answer exploited= False exploited_known= True HUMAN_REVIEW
details missing: osv_details_missing exploited= False exploited_known= True HUMAN_REVIEW

With the KEV download marked failed, the same state returns exploited_known False and URGENT_HUMAN_REVIEW, which shows the inconsistency. After the change in the working copy, both OSV paths return exploited_known False and URGENT_HUMAN_REVIEW. The full test suite passes (408 passed, 2 skipped).

## Impact

An affected component with an unanswered OSV query and a KEV-listed CVE is shown with exploited False and exploited_known True, and its action is HUMAN_REVIEW instead of URGENT_HUMAN_REVIEW. The output asserts a check that did not happen. The run is still marked RESULT INCOMPLETE, so the operator is warned, but the per-finding urgency and the stored finding record are wrong.

## Counterevidence

The CLI prints RESULT INCOMPLETE for any run with an OSV failure and warns about data gaps, and the exit code is non-zero, so the operator is warned that the run is not trustworthy. The change only affects the urgency label and the stored exploited_known value, not the exploited flag or the affected status. A KEV-listed CVE for a component whose OSV answer is missing would still not be found, which is an OSV data gap rather than a matcher decision. Components without a purl are the same invariant but are left as a policy question.

## What Would Change This Severity

Evidence that the run summary alone is used for triage (so the per-finding action is never read) would not raise the rating, while evidence that a KEV-listed affected component routinely has an OSV no-answer at run time would raise it to medium.

## Technical Analysis

evaluate hands every finding an exploited_known flag. For findings with a usable CVE list, the flag is computed from the KEV freshness and from invalid evidence files. For three paths the code passes the KEV freshness itself, although no CVE of the component was looked up:

```python title=src/matcher.py startLineNumber=396 endLineNumber=396
            findings.append(_finding(component, None, UNKNOWN, "osv_gave_no_answer", exploited_known=kev_ok))
```

The same pattern appears at line 401 (osv_details_missing) and line 413 (record_malformed). With a fresh KEV list, `exploited_known` becomes True, and `action_for` then returns HUMAN_REVIEW for an UNKNOWN finding. The code's own rule for the KEV-failed case is that an unchecked exploitation status must be urgent (test_failed_kev_download_never_turns_into_not_exploited expects URGENT_HUMAN_REVIEW), so the same state is handled inconsistently depending on whether the KEV feed failed or OSV failed. The paths on the same lines are reached when the purl has no OSV answer, when a listed advisory cannot be downloaded or validated, or when the advisory cannot be evaluated.

## Proof of Concept

1. Run from the repository root with the project's Python environment.
2. Build a component for pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1 and a feed set where OSV gave no answer for that purl (purl_vulns value None), with a fresh KEV list that contains CVE-2021-44228.
3. Run the CRA evaluation step and read the single finding.
4. The correct record marks exploited_known as False and the action as URGENT_HUMAN_REVIEW, because the component's CVEs were never checked against KEV.
5. Repeat with the advisory listed but its details missing (vulns value None) to see the same result.

```python
import sys
sys.path.insert(0, '.')
from src import matcher
from src.news_watcher import Feeds
from src.sbom_reader import Component
purl = 'pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1'
component = Component('log4j-core', '2.14.1', purl, 'maven', 'OK')
no_answer = Feeds(kev_ids={'CVE-2021-44228'}, kev_status={'status': 'ok'}, purl_vulns={purl: None}, vulns={})
finding = matcher.evaluate([component], no_answer)['findings'][0]
print('no OSV answer:', finding['rule'], 'exploited=', finding['exploited'], 'exploited_known=', finding['exploited_known'], finding['action'])
missing = Feeds(kev_ids={'CVE-2021-44228'}, kev_status={'status': 'ok'}, purl_vulns={purl: ['GHSA-jfh8-c2jp-5v3q']}, vulns={'GHSA-jfh8-c2jp-5v3q': None})
finding = matcher.evaluate([component], missing)['findings'][0]
print('details missing:', finding['rule'], 'exploited=', finding['exploited'], 'exploited_known=', finding['exploited_known'], finding['action'])
```

## Remediation

On the three paths where no CVE list was obtained (no OSV answer, advisory details missing, and an advisory that cannot be evaluated), record exploited_known as False, so the finding follows the same urgent-review rule that already applies to a failed KEV download. Apply the same invariant to components without a purl, which currently pass the KEV freshness as well; that change alters the urgency of every component without a purl, so the maintainers should confirm it as product policy before it is made.
