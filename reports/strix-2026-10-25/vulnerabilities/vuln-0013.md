# Run record above 20 MB is silently skipped by cra status, which then reports the previous clean run as current

**ID:** vuln-0013
**Severity:** LOW
**Found:** 2026-10-25 15:46:02 UTC
**Target:** cra CLI (local): src/news_watcher.py load_runs
**Endpoint:** cra status --runs
**Method:** LOCAL
**CWE:** CWE-390
**CVSS:** 3.1
**Confidence:** Medium
**Fix Effort:** Low

## Description

cra run saves its full result, including every finding, with no size limit, but cra status silently skips any run file over its 20 MB read cap. An SBOM with many duplicate components can push the saved run past that cap, so cra status reports an older complete run as the latest run with exit code 0, even when the skipped run contains a REPORT CASE.

## Evidence

Local test on the same runs folder: the saved run file is 50530757 bytes with 88007 findings, report_cases 2, complete true. cra status output: Last successful run: 2026-10-25T15:32:29.845876+00:00 followed by Latest run: all sources ok. with exit code 0; the newer run file is not used. A 24 MB run file (42515 findings) gives the same false result. A 14 MB run file (25508 findings) in the same folder gives WARNING: the latest run found 2 REPORT CASE finding(s) (affected AND actively exploited). Check the 24-hour deadline. with exit code 1, which shows the size cap is the only difference. With the fix applied in the working copy, the 24 MB file is reported as WARNING: RESULT INCOMPLETE with run_file: failed - the saved run is too large to read and exit code 1.

## Impact

The status command, which is the scheduled health check, can show a false all-clear while the latest run found an affected and actively exploited component. The run command itself still prints the REPORT CASE and exits with code 3, so the loss is limited to the status view and to operators who rely on it. The effect is an incorrect integrity signal for the early-warning check, with no confidentiality or availability impact.

## Confidence Rationale

## What Would Change This Severity

If the scheduled job exposes only the status exit code to an alerting system with no other review, the rating rises to Medium; if the run command output is always reviewed, it drops to informational.

## Technical Analysis

save_run writes the full run dictionary, including result.findings with one entry per component and advisory, using json.dumps with indent 2 and no size check (news_watcher.py save_run and _write_json_atomic). load_runs calls _read_json for each file, and _read_json returns None when the file is larger than MAX_CACHE_FILE_BYTES (20 MB), so load_runs drops the file silently because it is not a dict. status_summary then takes the newest remaining file as last and prints Latest run: all sources ok when that older run was complete. The SBOM controls the size: duplicate component entries each produce a full set of findings for the same advisories. A live run with 1000 identical pypi django 1.0.1 components plus one maven log4j-core 2.14.1 component produced 88007 findings and a 50.5 MB run file. A 14 MB run file from a smaller SBOM (25508 findings) is still read, so the cap is reachable from a small SBOM. This is distinct from the already-filed planted-run-file finding, because the file is written by the tool itself and the defect is the silent skip.

## Remediation

Never skip a run file silently. When a run file exists but is too large or unreadable, status must treat it as the latest run and report it as incomplete, using the file modification time as its time. Also keep saved runs within a size the reader accepts, or raise the reader limit to match the writer, so a legitimate run is not dropped.

## Fix Verification

Gate 1 security closure: in the patched copy an oversized latest run file now becomes a placeholder run with complete false and a run_file source marked failed, so status prints RESULT INCOMPLETE and exits with code 1 instead of showing the older run as all sources ok. Gate 2 bypass review: the placeholder uses the file modification time, so it sorts as the newest file as intended; unreadable but small files keep the existing behaviour, which the existing test test_a_damaged_run_file_is_ignored still checks. The remaining gap is that a run file far above the cap but still written by the tool keeps being read as failed rather than being re-read, which is the intended safe outcome. Gate 3 preserved behavior: the 14 MB run file still produces the REPORT CASE warning; the healthy runs still give all sources ok. Gate 4 how checked: executed, the status command on a 24 MB run file (now RESULT INCOMPLETE, exit 1) and on a 14 MB run file (REPORT CASE warning), plus python3 -m pytest in the working copy (412 passed, 2 skipped, including a new regression test test_an_oversized_latest_run_file_is_never_skipped). Not executed: a run through the full scheduled workflow on a real Task Scheduler host.

## Assumptions

An earlier complete run exists in the same runs folder, and the operator relies on cra status rather than the console output of cra run. The SBOM may come from a third party or be large in the operator's own environment.
