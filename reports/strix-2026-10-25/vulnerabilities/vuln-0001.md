# Planted run file in the runs folder makes cra status report a healthy latest run

**ID:** vuln-0001
**Severity:** LOW
**Found:** 2026-10-25 15:35:52 UTC
**Target:** cra CLI (local, src/news_watcher.py status_summary / run_is_complete / load_runs)
**Endpoint:** cra status --runs &lt;folder&gt;
**Method:** LOCAL
**CWE:** CWE-345
**CVSS:** 3.3
**Confidence:** High
**Fix Effort:** Medium

## Description

A run record placed in the `--runs` folder with a newer `finished_at` and self-declared healthy fields replaces the genuine latest run in `cra status`. The status output then reads "Latest run: all sources ok." and exits 0, hiding a genuine REPORT CASE finding that the real run recorded.

## Evidence

With the planted file present, `status` prints `Last successful run` with the planted time and `Latest run: all sources ok.`, and no REPORT CASE warning is printed. The exit code changes from 1 to 0. The genuine record that says `report_cases: 2` is still present in the folder but is no longer consulted. Reproduced at `/workspace/poc-output/poc/poc_planted_run_status.py` in the copy.

## Impact

The `status` command is the operator's only safety signal between scheduled `cra run` calls. With write access to the runs folder, a single file hides an earlier REPORT CASE warning and makes status exit 0 with a fresh "last successful run" time. The integrity of the status verdict depends entirely on the folder contents. Confidentiality and availability are not affected. Integrity impact is limited to the operator-visible status verdict.

## Counterevidence

1. The project explicitly accepts this. PLAN.md section (b) and PROGRESS.md ("Cache and run files can be edited by anyone with write access to the project folder ... accepted") say that fingerprints would only guard against mistakes, and the README is to say so. This report therefore reports a known, accepted limitation, not an unknown bug. 2. The attacker needs local write access to the project folder. The same access already allows editing `evidence/` and the cache, so this is not a privilege gain. The attacker is not the SBOM supplier in the threat model. 3. Future-dated files are rejected (`last_time <= current` and the "dated in the future" warning), so the attacker must date the file within the window. This does not stop the attack, but it constrains it. 4. The genuine run record is not deleted, so a human who reads the folder can still see it. 5. The status command still prints the "26-hour" and reporting-deadline notes. None of these stop a file that declares healthy fields from being trusted. The check that ran was: does the latest record's own flags say complete, and it does.

## What Would Change This Severity

Raise to Medium if the runs folder can be written by a different principal than the operator (a shared network folder, a scheduler account, or a sync tool), or if an automated consumer (alerting, dashboard, Power BI from PLAN.md phase 5) treats `status` exit 0 as an all-clear. Lower to Informational if the README warning on accepted local write access is confirmed in the shipped docs.

## Technical Analysis

`status_summary` takes the latest run as `runs[-1]` after `load_runs` sorts every `*.json` file in the runs folder by its own `finished_at` value. It then decides health from fields the file itself declares: `run_is_complete` checks only `complete is True` and that every entry in `sources` has `status == "ok"` (`src/news_watcher.py:585-594`). The other health checks (`report_cases`, `needs_human`, `components.unchecked`, `result.data_gaps`, `sbom_warnings`) are also read straight from the same file. Nothing in the code binds a run record to the process that wrote it. There is no digest, no sequence number, and no cross-check against the genuine run history.

The only protection against a future-dated planted run is `last_time <= current`. A planted file dated slightly before "now" passes it. The project records this as an accepted residual risk (PROGRESS.md, "Cache and run files can be edited by anyone with write access to the project folder", and PLAN.md section (b)). This report keeps the finding visible because the README warning and status wording are the only mitigation, and status presents the result as a verdict.

## Proof of Concept

1. In the copy of the project, run a genuine-looking latest run record in a temporary runs folder: `complete` false, `report_cases` 2, `needs_human` true, `finished_at` two hours ago.
2. Run `python -m src status --runs <folder>`. It reports "the latest run found 2 REPORT CASE finding(s)" and exits 1.
3. Write a second `*.json` file into the same folder with a name in the normal stamp format, `finished_at` one hour ago, `complete` true, `report_cases` 0, `needs_human` false, and healthy `sources`, `components` and `result` values.
4. Run `python -m src status --runs <folder>` again. The output reads "Latest run: all sources ok." with no REPORT CASE warning, and the exit code is 0.

## Code Analysis

**Location 1:** `src/news_watcher.py` (lines 585-594)
  Root control: run_is_complete trusts self-declared complete and sources flags with no cross-check or integrity check

**Location 2:** `src/news_watcher.py` (lines 601-612)
  Loader: load_runs trusts every *.json file in the runs folder and sorts by its own finished_at

**Location 3:** `src/news_watcher.py` (lines 658-659)
  Sink: status prints the healthy verdict from the file's own flags

## Remediation

Treat the status verdict as only as trustworthy as the runs folder, and make that explicit. Two options for the project owner to decide. (a) Add an integrity seal to each run record at save time (a digest of its canonical content, verified in `load_runs`, with unsealed or mismatched files treated as unreadable and surfaced as a warning). This stops accidental and naive edits, not a determined local writer, and needs a decision on key handling. (b) Keep the current design but have `status` print a visible warning when the newest run file is not the newest file written by the tool, and document the limit in the README. Whichever option is chosen, make sure a file that cannot be verified never produces "Latest run: all sources ok.".
