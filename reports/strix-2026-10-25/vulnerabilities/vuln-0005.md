# Same-version range boundaries misordered, hiding reintroduced affected versions

**ID:** vuln-0005
**Severity:** LOW
**Found:** 2026-10-25 15:43:28 UTC
**Target:** cra-scan (src/matcher.py)
**Endpoint:** src/matcher.py::_intervals
**Method:** N/A
**CWE:** CWE-697
**CVSS:** 3.7
**Confidence:** High
**Fix Effort:** Trivial

## Description

The OSV range walk in the CRA matcher sorts a fixed boundary before a later introduced boundary at the same version. A version that is affected again after the reintroduction is therefore computed as not affected. The evaluation step then reports it as UNKNOWN, so an actively exploited (KEV-listed) affected component gets urgent human review instead of a report case.

## Evidence

Observed on the unpatched code, run from the repository root:

match_vulnerability: ('NOT_AFFECTED', 'maven_numeric_range')
evaluate: UNKNOWN osv_says_affected_but_our_check_disagrees exploited=True action=URGENT_HUMAN_REVIEW

Expected per OSV range semantics: AFFECTED for 2.14.1 and action REPORT_CASE.

Differential check of the range walk against a state-machine reference over generated ECOSYSTEM ranges (PyPI and Maven, 15,000 records each): 1,051 and 864 false negatives respectively, all involving a start and an end at the same version, and zero false positives. After the ordering change the same checks return zero false negatives and zero false positives, and all 100 matcher tests still pass.

## Impact

A component affected by a KEV-listed vulnerability through a same-version reintroduction is routed to URGENT_HUMAN_REVIEW instead of REPORT_CASE. The matcher's direct result for the same version is NOT_AFFECTED. Demonstrated with a crafted OSV-style record; the scope is limited to range shapes with a same-version end and start inside one range.

## Counterevidence

The shape requires one range to contain a same-version end and start. In the saved OSV fixtures (50 ECOSYSTEM ranges) no such pair occurs, so this is not produced by the data observed so far. The defect is also masked by design in the evaluation step: a NOT_AFFECTED from the matcher is never shown as NOT_AFFECTED, so the wrong result appears as UNKNOWN with human review rather than as a silent safe answer, and the action is still urgent when the CVE is exploited. The defect does not affect the other range types or the exact version lists.

## What Would Change This Severity

Evidence that real OSV feeds publish same-version reintroduction pairs inside a single range would raise this to medium. Evidence that the only way to reach it is a crafted or compromised feed record would keep it low.

## Technical Analysis

_intervals converts OSV introduced, fixed and last_affected events into start, end and inclusive spans. It sorts the parsed events by (version, is_end), so at an equal version every start is placed before every end. The loop then skips a start while a span is already open. For a range introduced 2.0-beta9, fixed 2.12.2, introduced 2.12.2, the sorted order is introduced 2.0-beta9, introduced 2.12.2, fixed 2.12.2. The second start is skipped as redundant, and the fixed event closes the span at 2.12.2. The span that the event list describes as open from 2.12.2 onward is lost, so the version 2.14.1 falls outside every span and match_vulnerability returns NOT_AFFECTED (maven_numeric_range). Only the written order distinguishes this case from a zero-width span, so ties must keep the order in which the events were written. evaluate passes osv_listed=True, so the matcher's NOT_AFFECTED is converted to UNKNOWN (osv_says_affected_but_our_check_disagrees). For a KEV-listed CVE this yields URGENT_HUMAN_REVIEW rather than REPORT_CASE.

## Proof of Concept

1. Run from the repository root with the project's Python environment, which has the packageurl and packaging dependencies installed.
2. Load an OSV-style record for org.apache.logging.log4j:log4j-core whose single ECOSYSTEM range is introduced 2.0-beta9, fixed 2.12.2, introduced 2.12.2, and whose alias is the KEV-listed CVE-2021-44228.
3. Check pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1. The reintroduction at 2.12.2 is open-ended, so 2.14.1 is affected; the correct answer is AFFECTED.
4. Evaluate the same component with a KEV list containing CVE-2021-44228. The correct action is REPORT_CASE.

```python
import sys
sys.path.insert(0, '.')
from src import matcher
from src.news_watcher import Feeds
from src.sbom_reader import Component
record = {
    'id': 'GHSA-example-0000-0001',
    'aliases': ['CVE-2021-44228'],
    'affected': [{
        'package': {'ecosystem': 'Maven', 'name': 'org.apache.logging.log4j:log4j-core'},
        'ranges': [{'type': 'ECOSYSTEM', 'events': [
            {'introduced': '2.0-beta9'},
            {'fixed': '2.12.2'},
            {'introduced': '2.12.2'},
        ]}],
    }],
}
purl = 'pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1'
print('match_vulnerability:', matcher.match_vulnerability(purl, record, osv_listed=False))
component = Component('log4j-core', '2.14.1', purl, 'maven', 'OK')
feeds = Feeds(kev_ids={'CVE-2021-44228'}, kev_status={'status': 'ok'},
              purl_vulns={purl: [record['id']]}, vulns={record['id']: record})
finding = matcher.evaluate([component], feeds)['findings'][0]
print('evaluate:', finding['status'], finding['rule'], finding['exploited'], finding['action'])
```

## Code Analysis

**Location 1:** `src/matcher.py` (line 112)
  Sort range events so the written order decides ties at the same version

  **Suggested Fix:**
```diff
-     parsed.sort(key=lambda item: (item[0], item[1]))  # at the same version a start comes first
+     parsed.sort(key=lambda item: item[0])  # same version: keep the order the events were written in
```

## Remediation

Keep the order in which range events were written when two events share a version, instead of forcing every start before every end. Then the reintroduction at the same version is applied after the preceding fixed event, and the open span is kept. Add a regression test with a same-version fixed and introduced pair, asserting AFFECTED for a version after the reintroduction and an UNKNOWN or AFFECTED result (never NOT_AFFECTED) for a reversed-order tie.
