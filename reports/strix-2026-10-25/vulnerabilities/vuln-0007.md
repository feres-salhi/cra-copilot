# Substituted CISA KEV list is accepted as complete, silently dropping exploited CVEs

**ID:** vuln-0007
**Severity:** MEDIUM
**Found:** 2026-10-25 15:44:02 UTC
**Target:** cra-scan CLI, KEV download (www.cisa.gov known_exploited_vulnerabilities.json), src/news_watcher.py
**Endpoint:** cra run (fetch_kev -> validate_kev)
**Method:** GET
**CWE:** CWE-345
**CVSS:** 5.9
**Confidence:** High
**Fix Effort:** Medium

## Description

The KEV completeness check in `cra run` accepts any structurally valid KEV list whose count does not fall more than 5% below the highest count seen before. A network attacker who can intercept the CISA KEV download can remove two known-exploited entries and the tool still reports the KEV source as `ok` and the run as complete. A product whose affected component is actively exploited is then downgraded from REPORT CASE to RECORD.

## Evidence

Reproduction against the unmodified source (the lines are the output of the reproducer above):

```text
1. genuine list      : ok - downloaded and checked
2. list minus 2 CVEs : ok - downloaded and checked
   CVE-2021-44228 still in the list handed to the matcher: False
3. same, padded with 2 invented ids: ok - downloaded and checked
```

End-to-end `cra run` with the same affected SBOM (one log4j-core 2.14.1 component), before and after the omission:

```text
S0 good feed (1754 entries)
  Source KEV: ok - downloaded and checked
  exit=3 run.complete=True
  [REPORT CASE] log4j-core 2.14.1: GHSA-jfh8-c2jp-5v3q (CVE-2021-44228) -> AFFECTED - ACTIVELY EXPLOITED per kev
S1 feed silently omits CVE-2021-44228 and CVE-2021-45046 (1752 entries, count=1752)
  Source KEV: ok - downloaded and checked
  exit=1 run.complete=True
  finding: action RECORD, exploited false
```

After the fix, the same omission is rejected and the good copy is kept:

```text
2. list minus 2 CVEs : stale - download failed (KEV no longer lists entries that were in the saved copy); using the saved copy
3. same, padded with 2 invented ids: stale - download failed (KEV no longer lists entries that were in the saved copy); using the saved copy
```

## Impact

An on-path attacker who can serve a modified CISA KEV response can (a) remove specific known-exploited CVEs so that affected components are reported as not exploited, turning a REPORT CASE (the 24-hour early-warning clock) into a RECORD, while the run record and `cra status` show "all sources ok" and `complete: true`; and (b) replay the previous KEV list with an advanced `dateReleased`, so CVEs added in the genuine update are absent from the run for the intercepted run. The tool gives no warning for either case.

## Counterevidence

The strongest case against this finding: (1) the attacker needs a TLS-trusted interception position for a US government host, which is a high bar. The Python default verification is on (`http_fetch`), so a plain network attacker without a trusted certificate is rejected; this is why AC is H. (2) The 5% tolerance is a deliberate design choice, documented in `MAX_KEV_DROP` and enforced by a test, so the tool does not claim to detect every omission. (3) The run is not silent in the narrow sense: `Source KEV: ok` is printed. The counterpoint is that the status line says `ok - downloaded and checked`, which asserts completeness that the code cannot verify, and the run record is marked `complete: true`. (4) The first run has no baseline, and the list shrink check is relative to a previous good copy. The replay variant needs no removal and is not stopped by any control in the repository. I did not find a control that prevents the on-path substitution itself.

## Confidence Rationale

The validation logic was exercised end to end on the real TLS download path (`http_fetch`, `fetch_kev`, `validate_kev`, matcher, run record) with a locally trusted certificate; the interception itself is simulated, which is the attacker-position assumption.

## What Would Change This Severity

Demonstrating the interception from an unprivileged network position (for example an open network with a trust anchor an attacker can install) would raise the attack complexity assessment and the rating to High; adding an integrity check on the KEV file (signature or pinned content) would lower it to Low.

## Technical Analysis

The KEV download is validated in `validate_kev` and stored by `fetch_kev`. The only protection against a shortened list is a count tolerance:

```python title=src/news_watcher.py startLineNumber=224 endLineNumber=225
    if saved_max_count and len(entries) < saved_max_count * (1 - MAX_KEV_DROP):
        return "KEV count dropped by more than 5% compared with the highest count seen before"
```

`MAX_KEV_DROP` is `0.05` (`src/news_watcher.py:46`). The check only compares cardinality, so removing any number of entries up to 5% of the list is accepted, and removing entries while adding the same number of invented CVE ids (which pass the CVE pattern, uniqueness and date checks) is also accepted. The download is then stored as a good copy in `fetch_kev` (`src/news_watcher.py:253-254`, `_write_json_atomic` at the end of `fetch_kev`), `status` is set to `ok`, and `Feeds.sources_ok`/`complete` report the run complete. Nothing in the matcher cross-checks the KEV list against the previous copy; `exploited_status` only tests membership in `kev_ids`.

The removal in the proof of concept targets the two KEV entries that are the only KEV links for the affected log4j-core 2.14.1 records (CVE-2021-44228 and CVE-2021-45046). Removing both is 0.11% of the list, far below the 5% tolerance. The 5% tolerance is explicitly tested as intended behaviour (`tests/test_news_watcher.py`, "drop of less than 5 percent is accepted"), so the design choice itself is the root of the completeness gap: the tool asserts completeness and freshness from structure alone.

Replay variant: `validate_kev` only rejects a `dateReleased` older than the saved copy. An on-path response that carries the previous entries with a newer `dateReleased` passes, is saved, and is reported `ok`. A later uninterrupted run then recovers the new entries, so the effect lasts for the intercepted run(s).

The first run has no saved copy and no baseline, so any list of 1000 or more entries is accepted as complete on the first download. This is a related residual and is not separately demonstrated here.

Git history is not available in the checked-out source, so no commit attribution is given.

## Proof of Concept

1. Start from the repository's saved KEV list (1754 entries, includes CVE-2021-44228 and CVE-2021-45046), and a clean cache folder.
2. Run `cra run` with a single affected component (log4j-core 2.14.1) and a KEV download that is served over TLS from an on-path position. The genuine download produces a REPORT CASE and exit code 3.
3. Serve a KEV list that is structurally valid (count equals the number of entries, all cveID and dateAdded fields well formed, unique IDs, newer or equal dateReleased) and omits CVE-2021-44228 and CVE-2021-45046.
4. Observe that the KEV source is reported `ok - downloaded and checked`, the run record has `complete: true`, the finding is `RECORD` with `exploited: false`, the exit code drops to 1, and the saved KEV copy no longer contains the two CVEs.
5. Repeat step 3 with the omitted list padded by two invented valid CVE identifiers so that the entry count is unchanged; the same result occurs.

```python
import copy
import json
import sys
import tempfile
from datetime import datetime, timezone
from pathlib import Path

repo = Path(sys.argv[1])
sys.path.insert(0, str(repo))
import src.news_watcher as nw  # noqa: E402

kev = json.loads((repo / "tests" / "fixtures" / "kev.json").read_text())
now = lambda: datetime(2026, 10, 25, 12, 0, 0, tzinfo=timezone.utc)  # noqa: E731
cache = Path(tempfile.mkdtemp())


def fetch(data):
    return lambda url, body=None, max_bytes=0: json.dumps(data).encode()


_, status = nw.fetch_kev(cache, fetch(kev), lambda s: None, now)
print("1. genuine list      :", status["status"], "-", status["detail"])

omitted = copy.deepcopy(kev)
omitted["vulnerabilities"] = [e for e in omitted["vulnerabilities"] if e["cveID"] not in {"CVE-2021-44228", "CVE-2021-45046"}]
omitted["count"] = len(omitted["vulnerabilities"])
data, status = nw.fetch_kev(cache, fetch(omitted), lambda s: None, now)
print("2. list minus 2 CVEs :", status["status"], "-", status["detail"])
print("   CVE-2021-44228 still in the list handed to the matcher:", any(e["cveID"] == "CVE-2021-44228" for e in data["vulnerabilities"]))

padded = copy.deepcopy(omitted)
padded["vulnerabilities"] += [{"cveID": f"CVE-2026-9{i:04d}", "dateAdded": "2026-10-20"} for i in (1, 2)]
padded["count"] = len(padded["vulnerabilities"])
cache2 = Path(tempfile.mkdtemp())
nw.fetch_kev(cache2, fetch(kev), lambda s: None, now)
_, status = nw.fetch_kev(cache2, fetch(padded), lambda s: None, now)
print("3. same, padded with 2 invented ids:", status["status"], "-", status["detail"])
```

## Remediation

Reject any new KEV list that does not contain every CVE identifier in the saved copy, and do not allow a count tolerance below the highest count seen. Treat a list that fails this check as `stale` so the run is marked incomplete and the saved copy is kept. Add an authenticity check on the KEV file (a signature or a pinned content hash) before its content is treated as complete, because a structural check cannot detect a replay of the previous list with a newer date. Before merging, confirm CISA's policy on removing entries, since a legitimate removal would then block later downloads until the saved copy is deleted.

## Fix Verification

Gate 1, applicability: the patch was applied to a copy of the repository. The diff touches only `src/news_watcher.py` and `tests/test_news_watcher.py`; the location blocks match the original text character for character. The `MAX_KEV_DROP` line (46) is informational here: the fix removes it, so it is not an applicable replacement block.

Gate 2, security closure: re-ran the reproducer against the patched copy. The omitted list (two CVEs removed) and the padded list (two CVEs removed, two invented ids added) are both rejected with `KEV no longer lists entries that were in the saved copy`, and the saved copy keeps CVE-2021-44228. End-to-end `cra run` with the same omission now yields `Source KEV: stale`, `run.complete=False`, and the saved copy still lists both CVEs. Closure is verified for removal of entries that were in the saved copy.

Gate 2 gap: the replay variant (old list, newer `dateReleased`) is not closed. The patched code accepts it and the new genuine CVE is absent for the intercepted run. Closing it needs content authenticity (signature or pinned hash) or a second source, which is outside a local structural check. This patch does not claim to close it.

Gate 3, bypass review: traced the changed branch from `fetch_kev` only; `validate_kev` is also called by `load_kev_cache` with no saved ids, so cached-copy loading is unchanged. Tried the padded omission (rejected) and a clean superset with a higher count (accepted, correct). The count check remains as a second guard against a shrinking watermark.

Gate 3 gap: a list that adds new entries and drops none is still accepted; that is correct behaviour, but it means a suppressed genuine update is only detected on a later uninterrupted run.

Gate 3 trade-off to confirm with maintainers: if CISA ever legitimately removes an entry from KEV, the new check will mark every later download `stale` until the saved copy is deleted. I could not verify CISA's removal policy offline, so this is stated as an open decision, not as a known fact.

Gate 3 residual: the first run (no saved copy) still accepts any list of 1000 or more entries.

Gate 4, preserved behaviour: the public functions keep their signatures (`validate_kev` gains an optional trailing argument). The normal path (`genuine list: ok`) and the replay-rejection path (older `dateReleased`) are unchanged.

Gate 5, repository checks: `python3 -m pytest -q` in the copy: 411 passed, 2 skipped (baseline before changes: 408 passed, 2 skipped). The test `test_kev_drop_of_less_than_5_percent_is_accepted` was replaced by `test_kev_drop_of_a_single_entry_is_rejected_and_old_copy_kept`, and `test_kev_omission_padded_with_invented_ids_is_rejected` was added. The 5% test message assertion was updated to the new message. The 2 skipped tests are the live network tests that require `CRA_LIVE_TEST=1`.

## Assumptions

The attacker controls the network path between the operator and www.cisa.gov (for example, TLS interception with a certificate the operator's system trusts, or a compromised upstream serving the file). The operator runs `cra run` against the default KEV URL. No independent integrity check of the KEV file (signature or pinned hash) exists in the tool.
