# Slash-separated or upper-case Maven purl is accepted as OK and silently clears an exploited component

**ID:** vuln-0004
**Severity:** MEDIUM
**Found:** 2026-10-25 15:42:15 UTC
**Target:** cra CLI (local): src/sbom_reader.py (_read_component) and src/cli.py (run)
**Endpoint:** cra run --sbom
**Method:** LOCAL
**CWE:** CWE-1289
**CVSS:** 5.5
**Confidence:** High
**Fix Effort:** Low

## Description

A CycloneDX component whose Maven purl uses a slash-separated namespace, such as `pkg:maven/org/apache/logging/log4j/log4j-core@2.14.1`, or an upper-case group or artifact spelling, is accepted as a valid component. OSV does not match these spellings, so `cra run` reports the component as checked with zero findings, a complete result, and exit code 0. The canonical form of the same component is affected by CVE-2021-44228, which is listed in CISA KEV.

## Evidence

Slash-separated namespace, complete run with zero findings: `Components checked: 1, not checkable (UNKNOWN): 0` then `No exploited vulnerabilities found in the checked components (all sources ok).` and exit code 0. Canonical namespace, same component and same feeds: `[REPORT CASE (affected AND actively exploited - the 24-hour clock may be running)] log4j-core 2.14.1: GHSA-jfh8-c2jp-5v3q (CVE-2021-44228) -> AFFECTED [osv_exact_version_list] - ACTIVELY EXPLOITED per kev (CVE-2021-44228)` and exit code 3. Live OSV querybatch for pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1 returns 7 advisories; the same query with pkg:maven/org/apache/logging/log4j/log4j-core@2.14.1, pkg:maven/ORG.apache.logging.log4j/log4j-core@2.14.1 and pkg:maven/org.apache.logging.log4j/Log4j-Core@2.14.1 returns an empty result each. Run record for the slash form: complete true, report_cases 0, findings empty, packages empty.

## Impact

A supplier-supplied or hand-edited SBOM can make the tool report a vulnerable Maven component as clean. The run record is marked complete, the console prints `No exploited vulnerabilities found in the checked components (all sources ok)`, and `cra status` reports `Latest run: all sources ok.` A KEV-listed affected component is therefore never raised for the 24-hour early-warning decision. The same silence applies to every advisory for that component, not only the exploited one.

## Counterevidence

Checked: mainstream generators (CycloneDX Maven plugin, Syft) emit dot-separated canonical namespaces, so the trigger needs a hand-written, edited, or defective SBOM. This lowers likelihood but not the validity of the defect. Checked whether check-sbom or run surfaces anything: check-sbom prints OK and run prints only Components checked: 1, so the operator is not warned. Checked whether the matcher's osv_listed safety rule catches it: it does not, because OSV returned nothing to compare. Checked whether evidence files or KEV alone could raise the finding: no, KEV is keyed on CVE ids that come only from OSV records, and the record is never loaded. Checked whether the run is marked incomplete: it is marked complete. No control in the reader, matcher, or CLI prevents the silent clear for these spellings.

## What Would Change This Severity

The tool is a local CLI that reads a supplier-supplied SBOM file, so the attack vector is Local with user interaction required (the operator must run the file). If the SBOM were ingested automatically from a network channel without operator action, the rating would rise to High (7.5); cross-checking component identity against a second source would lower it to Low.

## Technical Analysis

The SBOM reader validates each component purl and then rebuilds a canonical purl from its parts. For Maven, the namespace is split on the slash character and every segment is accepted independently, so org/apache/logging/log4j passes as a namespace (sbom_reader.py lines 146 to 149). The group-field check only compares the purl namespace with its dotted form, so a matching group field also passes. The name and group checks use exact comparison, so upper-case spellings pass too. The canonical purl is then sent to OSV unchanged. OSV querybatch is case-sensitive and does not normalize slashes, so it returns no advisories for these spellings. In matcher.evaluate the component therefore has an empty advisory list, produces no finding, and is counted in checked. match_vulnerability only returns UNKNOWN when OSV listed the vulnerability for that purl, so nothing downstream notices the mismatch. feeds.complete is then true, so the run record and cra status both report success. An existing test, test_double_slash_in_a_namespace_is_cleaned_up_not_kept, pins the acceptance of the slash form as OK. Measured against live OSV on the same component: the canonical purl returns 7 advisories, including GHSA-jfh8-c2jp-5v3q (CVE-2021-44228, KEV-listed). The slash-namespace, upper-case group, and upper-case artifact variants each return 0 advisories. Root cause: the reader accepts non-canonical identifiers as equivalent to the canonical component without checking that they are spelled the way the vulnerability database spells them, and an absent advisory answer is treated as a clean result.

## Remediation

Reject Maven purl namespaces that contain a slash as non-canonical, since they must use dot-separated group ids. Refuse upper-case Maven group or artifact spellings as UNKNOWN until the tool can confirm the spelling OSV uses, because OSV's Maven matching is case-sensitive. Update the test that currently expects the slash form to be OK so that it expects UNKNOWN, and add regression tests for both forms. This converts the silent clean result for these spellings into UNKNOWN and RESULT INCOMPLETE for human review.
