# OSV vulnerability id with a trailing dot aborts the whole run

**ID:** vuln-0011
**Severity:** LOW
**Found:** 2026-10-25 15:45:12 UTC
**Target:** cra-scan CLI, OSV batch and detail download, src/news_watcher.py
**Endpoint:** cra run (_parse_batch_result -> fetch_osv -> _vuln_cache_path -> safe_join)
**Method:** POST
**CWE:** CWE-755
**CVSS:** 3.7
**Confidence:** High
**Fix Effort:** Trivial

## Description

The id pattern used for OSV responses accepts an identifier that ends with a dot, but the file-name check used when the id is turned into a cache path rejects it. A feed response that lists such an id raises an uncaught `ValueError` inside `fetch_osv`, which aborts `cra run` for every component. The run is recorded as an internal error and is not completed.

## Evidence

Unmodified source, `cra run` with one component and the saved KEV fixture:

```text
RESULT INCOMPLETE - internal error (ValueError). Do not rely on this run.
A record of this failed run was saved; `cra status` will show it.
exit 1
status: WARNING: RESULT INCOMPLETE - the latest run was not fully successful. Do not rely on it.
```

Direct call on the unmodified source:

```text
UNCAUGHT ValueError unsafe file name
```

After the fix, the same response is treated as a malformed batch answer (no answer for the component), and the run reports the OSV source as `failed` with a normal message instead of an internal error:

```text
{'status': 'failed', 'detail': 'no answer from OSV and no saved answer for one component', 'purls_asked': 1}
```

## Impact

An on-path attacker who can serve one OSV batch response can stop every `cra run` from completing while that response is served. The tool fails safe (the run is marked incomplete and the operator is told), so no false "nothing found" result is produced; the impact is an availability loss for the scheduled check.

## Counterevidence

(1) The attacker needs the on-path position described above. (2) The run fails closed: the record is saved as incomplete and the output says so, so no wrong verdict is produced. (3) `safe_join` itself is correct: it rejects the name and no file is written outside the cache. The defect is the inconsistency between the two validators, and the consequence is an availability loss for the run, which is why the rating is Low. I checked that the id cannot reach a path outside the cache folder (the rejection happens before any write).

## Confidence Rationale

Reproduced directly on the unmodified `fetch_osv` and through the `cra run` safety net; the on-path response is simulated.

## What Would Change This Severity

If the abort were reachable without an on-path position (for example through a crafted SBOM value that the tool echoes back as an id), the rating would stay Low because the run still fails closed; a path that writes or reads outside the cache would be a separate, higher finding.

## Technical Analysis

The id is validated by `VULN_ID_PATTERN`, which accepts a trailing dot:

```python title=src/news_watcher.py startLineNumber=56 endLineNumber=56
VULN_ID_PATTERN = re.compile(r"(?!.*\.\.)[A-Za-z0-9][A-Za-z0-9._-]{0,63}")  # no ".." anywhere
```

The id then reaches `_vuln_cache_path`, which builds the file name `osv-<id>.json` and passes it to `safe_join`. `safe_join` rejects any name that ends with a dot (`src/safe_paths.py`, `name.endswith(".")`), so the same id is refused with a `ValueError`. The call site in `fetch_osv` is outside every `try` block:

```python title=src/news_watcher.py startLineNumber=511 endLineNumber=511
        path = _vuln_cache_path(cache_dir, vuln_id)
```

Only `FetchError` is caught in that loop, so the `ValueError` propagates to `collect` and `_run`. `_run` catches `Exception`, prints `RESULT INCOMPLETE - internal error (ValueError)` and saves a failed run record. The two validators agree on every other id class; the mismatch is limited to the trailing dot. Identifiers with a trailing dot do not occur in OSV data, which is why this is a robustness defect in a feed-controlled input rather than a data-integrity issue.

## Proof of Concept

1. Serve an OSV batch response whose result for one component lists a vulnerability with id `GHSA-abcd-efgh-ijkl.` (trailing dot), with a valid modified time.
2. Run `cra run` with an SBOM that contains that component and a valid KEV list.
3. Observe the internal-error abort, the failed run record, and that the other components are not reported.

```python
import json
import sys
import tempfile
from datetime import datetime, timezone
from pathlib import Path

repo = Path(sys.argv[1])
sys.path.insert(0, str(repo))
import src.news_watcher as nw  # noqa: E402

now = lambda: datetime(2026, 10, 25, 12, 0, 0, tzinfo=timezone.utc)  # noqa: E731


def fake(url, body=None, max_bytes=0):
    if url == nw.OSV_BATCH_URL:
        return json.dumps({"results": [{"vulns": [{"id": "GHSA-abcd-efgh-ijkl.", "modified": "2024-01-01T00:00:00Z"}]}]}).encode()
    raise nw.FetchError("unused")


try:
    print(nw.fetch_osv(["pkg:pypi/requests@2.30.0"], Path(tempfile.mkdtemp()), fake, lambda s: None, now)[2])
except Exception as error:
    print("uncaught:", type(error).__name__, error)
```

## Code Analysis

**Location 1:** `src/news_watcher.py` (line 56)
  Reject a trailing dot in an OSV vulnerability id when the batch answer is parsed

  **Suggested Fix:**
```diff
- VULN_ID_PATTERN = re.compile(r"(?!.*\.\.)[A-Za-z0-9][A-Za-z0-9._-]{0,63}")  # no ".." anywhere
+ VULN_ID_PATTERN = re.compile(r"(?!.*\.\.)[A-Za-z0-9](?:[A-Za-z0-9._-]{0,62}[A-Za-z0-9_-])?")  # no ".." anywhere, no trailing dot
```

## Remediation

Make the identifier pattern match exactly what the cache-path check accepts, so that a trailing dot is rejected when the batch answer is parsed. Also catch a rejected identifier at the call site in `fetch_osv` so that a single bad identifier cannot abort the whole run.

## Fix Verification

Gate 1, applicability: the regex change keeps the same maximum length (64 characters), keeps the single-character ids, and keeps the `..` lookahead. The original line 56 matches `fix_before`. The character class change only removes the trailing `.` case.

Gate 2, security closure: with the patched pattern, `GHSA-abcd-efgh-ijkl.` fails the batch-answer check, the component gets no answer, and the run reports `Source OSV: failed - no answer from OSV and no saved answer for one component` instead of an internal error. The `ValueError` can no longer arise from this id class.

Gate 3, bypass review: the other ways to reach `safe_join` with an unsafe name are the `..` lookahead, the slash and backslash exclusion, and the Windows device-name check; each was checked directly in the reproducer, and `safe_join` still rejects names that the pattern would now allow (for example `osv-a-.json` is allowed and is a plain name). Identifiers that differ only by a trailing dot are all rejected by the new pattern. An identifier of 64 characters ending in a letter is accepted, as before.

Gate 4, preserved behaviour: legitimate OSV identifiers (CVE-, GHSA-, PYSEC-, and others that do not end with a dot) are accepted unchanged; the test fixtures use only such ids.

Gate 5, repository checks: `python3 -m pytest -q` in the copy: 411 passed, 2 skipped, including the new parametrised case `GHSA-abcd-efgh-ijkl.` in `test_osv_invalid_vulnerability_id_is_rejected`.

## Assumptions

The attacker can answer the OSV batch request on the operator's behalf (on-path with a trusted certificate). The attacker needs no knowledge of the cache folder or the SBOM.
